# Multi-tenant SaaS and tenancy isolation

> Use this guide when a diagram has to show how a SaaS product keeps its tenants apart. That covers tenancy models, tenant routing, per-tenant data or keys, tenant context, noisy-neighbour controls, operator access, the control plane and cells.

## Questions to ask first

1. What is the tenancy model for each tier: compute, data and encryption keys? (default: pooled compute; one pooled database with a tenant ID column; one provider-managed key for the pooled store. Use a "bridge" design only if the user names a tier or tenant as dedicated.)
2. How is the tenant identified on each request: subdomain, path prefix, a claim in the access token or an API key? (default: subdomain for routing and a tenant claim in the token for authorization, with the gateway checking that both agree)
3. How many tenants or tenant tiers should appear? (default: three example tenants, A, B and C, all pooled and labelled as examples. Add a dedicated tenant only if question 1 names a dedicated tier.)
4. How does tenant context reach the data tier and services? Options are a per-request session variable, a per-tenant database role or credential, or an app-level WHERE clause. Do services use one shared role, a role per tenant, or a token vending service that issues tenant-scoped credentials? Which roles bypass the check? Do background workers and event consumers re-derive tenant context, or do they trust the tenant ID in the message? (default: row-level security driven by a session variable set inside each transaction; one shared service role without bypass rights, labelled as shared; workers take the tenant ID from the message and set the same context before touching data)
5. Who controls the encryption keys? Options: the provider; the tenant importing key material into the provider's key service (BYOK); a key in the tenant's own cloud key-management account that the provider uses through a cross-account grant (often marketed as CMK or BYOK); a key held outside the provider (HYOK); or client-side encryption. If tenants have their own keys on pooled data, is encryption done at the storage level or per record in the application? (default: provider-managed; one key for pooled data, and a per-tenant key only for a tenant named as dedicated)
6. Do data-residency or compliance rules pin some tenants to a region or to dedicated infrastructure? Is the system split into cells, and how are tenants assigned to them? (default: one region and no cells. If cells exist, draw two cells, with tenants pinned by a cell router that reads a tenant registry.)
7. Which noisy-neighbour controls exist, and where are they enforced? Options include request rate limits, quotas, concurrency or connection limits at the database, and separate queues. Do shared caches, queues, search indexes or object stores hold tenant data, and how is each one partitioned? (default: one per-tenant rate limiter at the gateway after token validation; shared caches and queues with the tenant ID in every key and message; one object-store bucket with a prefix per tenant)
8. Who can access data across tenants, such as support staff, operators or migration jobs, and through what? How do per-tenant backup, restore, export and offboarding deletion work? (default: none of this is drawn. If operator access is drawn, it goes through privileged access with an audit log.)
9. Is the scope one request path, the whole platform, or a comparison of models? What does the control plane include? (default: one request path through the application plane, with a control plane beside it holding onboarding, provisioning, billing and metering, and a tenant registry)

## Push back when

- **Row-level isolation is described as "separate databases".** Rows tagged with a tenant ID and filtered by a policy live in one database instance. They share one backup, one failure domain and one set of administrator credentials. Tell the user the diagram will show one database with row-level security, and ask whether they mean that or a database per tenant.
- **Row-level security is presented as complete isolation.** It is only as strong as the role the application connects with. Table owners, superusers and roles with bypass rights skip the policies, and migrations or reporting jobs often run as those roles. A tenant variable set on a pooled connection can leak into the next request unless it is reset or scoped to the transaction. Ask which role the app uses and how the context is set, and put the answer in the database `detail`.
- **Per-tenant keys are claimed on a pooled database.** At-rest encryption of a shared database or volume uses one key. Per-tenant keys on pooled rows need envelope encryption in the application or per field, done before the write. Ask which one is used. If it is storage-level, draw one key for the pooled store.
- **A shared cache has no tenant in the key.** If two tenants can produce the same cache key, one tenant can be served another tenant's data. Ask whether keys carry the tenant ID or the cache is partitioned. Do not draw an unqualified shared cache as safe.
- **An object store uses one prefix per tenant under one shared policy.** If the service's credential can read the whole bucket, a code bug can read any tenant's objects. Ask whether credentials are scoped to the tenant's prefix or there is a bucket per tenant, and label what is true.
- **Per-tenant keys sit in one shared vault path with one access policy.** Any principal that can read that path can read every tenant's key, so the keys are separate in name only. Ask for the policy that scopes each service or tenant to its own key and draw it, or label the vault as a shared trust domain.
- **BYOK is described as "the provider cannot decrypt".** With BYOK, and with a key kept in the tenant's own account, the provider's service still uses the key to decrypt for the tenant. The tenant's control is to revoke or disable it. HYOK keeps key material outside the provider and lets the tenant cut access by refusing unwrap calls, but the running service still sees plaintext while it processes data. Only client-side encryption, where the provider never handles plaintext, means the provider cannot decrypt. Ask which guarantee is meant and label it on the diagram.
- **The tenant is taken from a client-supplied header or subdomain with no check.** A subdomain or header is a routing hint that anyone can change. Authorization and per-tenant limits need the tenant from a verified token or credential, and the gateway or service must check that the two agree.
- **Background workers trust the tenant ID in a message without checks.** Anyone who can publish to the queue can then act as any tenant, and a worker that drops the tenant ID can write data under the wrong tenant. Ask whether producers are authenticated and whether workers set tenant context before data access.
- **A Kubernetes namespace per tenant is described as strong isolation.** Namespaces share the cluster control plane, the nodes and the kernel. Pods in different namespaces can reach each other unless network policies block it. Ask whether network policies, separate node pools or separate clusters are used.
- **An edge rate limiter is presented as solving noisy neighbours.** It caps the request rate, not the cost of each request. A tenant can still saturate a shared database, its connection pool or a queue with a few expensive calls. Ask whether quotas also exist at the shared resource.
- **Cells are described as isolating every tenant.** A cell limits the blast radius to the tenants pinned to it. Tenants inside one cell still share it, and the cell router and tenant registry remain shared.

## How we draw it here

- **Direction.** Lay the diagram out left to right. Tenant users come first, then the edge (gateway or ingress), then the application plane, then data and keys on the right. Put the control plane in its own `panel` group above or below the application plane, never mixed into it.
- **Tenants and boundaries.** Draw a tenant as a `boundary` group only when its resources are actually separate: its own database, cluster, account, VPC or cell. Show pooled tenants as labels on shared components ("Orders service, pooled: tenants A, B, C") or as `detail` text, not as groups. Use a `boundary` for the provider's trust boundary and for each cell.
- **Planes.** Use two `panel` groups titled "Control plane" and "Application plane". Control-plane components: `software/microservice` for "Onboarding", `software/workflow` or `devops/infrastructure-as-code` for "Provisioning", `business/invoice` for "Billing", `observability/metrics` for "Usage metering", and `data/relational-db` or `data/key-value-db` for "Tenant registry".
- **Tenant identity and routing.** Use `identity/user` or `identity/group` for tenant users, `identity/identity-provider` for sign-in and `identity/access-token` labelled with the tenant claim. Use `network/api-gateway` or `kubernetes/ingress` for the tenant-aware entry point. Use `network/load-balancer` only if the user names one.
- **Tenant context and credentials.** Use `identity/service-account` for the role services use to reach data, labelled "shared" or "per tenant". For a token vending service, use a `software/microservice` labelled "Token vending" that issues an `identity/access-token` labelled "tenant-scoped". Draw `software/background-worker` with the source of its tenant context in `detail`.
- **Noisy-neighbour controls.** Place `resilience/rate-limiter` after token validation at the gateway, keyed on the verified tenant claim, with the limit in the label ("per tenant, 100 req/s"). If a pre-authentication limiter exists, label it "per IP" or "per client", not per tenant. Use `resilience/autoscaler`, a `software/message-queue` per tier or `resilience/circuit-breaker` only when the user names them.
- **Compute.** Use `software/microservice`, `kubernetes/namespace`, `kubernetes/cluster`, `kubernetes/deployment`, `cloud/vpc` or `cloud/cloud-region`, depending on the level of the story.
- **Data.** For pooled rows, use one `data/relational-db` whose `detail` names the mechanism, for example "RLS on tenant_id via SET LOCAL, app role without BYPASSRLS". Use one `data/relational-db` per tenant only for a database-per-tenant model. Give `data/cache` its key format, and give `storage/object-store` its prefix or bucket per tenant and the credential scope. Give `storage/backup` a `detail` with its restore scope ("whole store" or "per tenant").
- **Keys.** Draw an `identity/key` for each key that exists. Use `identity/secrets-vault` for the key store, with its path or policy in `detail`, and `security/policy-engine` for the policy that scopes key access. Use `hardware/hsm-device` only if the user states one. When per-tenant keys protect pooled data, put the envelope-encryption step in the service's `detail`. For a key in the tenant's own cloud account, or for HYOK, draw the tenant's key store inside the tenant's boundary, outside the provider boundary, with a `dependency` edge from the provider service labelled with the grant or unwrap call.
- **Operator access.** Use `identity/admin` for support staff and operators, reaching tenant data through `identity/privileged-access`, with an `observability/audit-log` recording each session. Draw this only when question 8 says so.
- **Observability.** When tenant-level telemetry matters, draw `observability/logs` or `observability/metrics` with `detail` saying they carry tenant_id and keep tenant payloads out.
- **Cells.** Use one `boundary` group per cell, each holding the same set of components. Outside the cells, draw a `network/api-gateway` or `software/microservice` labelled "Cell router" that reads the tenant registry.
- **Edge kinds.** Use `data` for requests and data movement and `control` for provisioning, configuration and policy pushed from the control plane. Use `dependency` for "uses key", "reads registry" or "assumes role" relations that are not request flow. Use `replication` only for real cross-region or cross-cell copies.
- **Comparisons.** For silo, pool and bridge, use three side-by-side `panel` groups with the same tiers in the same rows, so the reader compares like with like.
- **Palettes.** Give each dedicated tenant one palette and keep it the same across all panels. Use `slate` for pooled or shared resources and a separate palette for the control plane. Colour never replaces a label.
- **Legend and footer.** Add a `legend` whenever more than one edge kind or tenant palette appears. Use the `footer` to state the tenancy model per tier and any assumptions, for example "Compute pooled; data pooled with RLS; one provider-managed key; tenants are examples".

## Common mistakes

- Drawing every tenant as a boundary around shared services, which implies isolation the platform does not have.
- Merging control-plane services such as billing and onboarding into the request path, so they appear to handle every tenant request.
- Drawing one database icon per tenant when the design uses one database with a tenant column.
- Drawing one key per tenant on a pooled store that only has storage-level encryption.
- Showing a shared `data/cache`, `software/message-queue` or `storage/object-store` with no note of how tenant data is keyed, partitioned or scoped.
- Drawing a per-tenant rate limiter keyed on the subdomain or a header, or placing it before authentication. That lets one tenant use up another tenant's quota.
- Placing the rate limiter after the services it protects, or leaving out the key it limits on.
- Showing one `identity/secrets-vault` holding all tenant keys with no policy, presented as per-tenant key isolation.
- Drawing background workers or scheduled jobs with no tenant context, or with a broad role that silently reads every tenant.
- Labelling a key in the tenant's own account, or a HYOK store, as "provider cannot decrypt".
- Stand-ins a guessing model picks: `ai/router` for a tenant or cell router (that asset means an AI model router), `security/firewall` as a tenant boundary, `cloud/public-cloud` as a tenant, `security/microsegmentation` for row-level security, and a load balancer the user never mentioned.
- Showing a silo tenant and pooled tenants with different component sets in a comparison, which makes the difference look larger than it is.
- Adding a premium dedicated tenant, cells, regions, operator access or a second key service because "typical SaaS has them". Ask first.

## Start from

- `software-overview` for a single application plane with tenants as labels.
- `kubernetes-ingress` for tenant-aware routing through ingress into namespaces.
- `zero-trust-access` when the focus is tenant identity, token claims, policy enforcement or privileged operator access.
- `event-driven` when async workers and tenant context in messages are the focus.
- `backup-dr` when per-tenant backup and restore scope is the focus.
- For silo, pool and bridge comparisons and for cell layouts there is no template yet. Use `layout_diagram`, then arrange three comparison panels or one boundary per cell.
- Read alongside: `brief` first, then `cloud` and `software-architecture`, and `style` before export.
