# Delivery pipelines, supply chain and GitOps

> Use this guide when the diagram shows how a code change becomes a running release: CI/CD stages and gates, software supply-chain controls, GitOps or Helm delivery, infrastructure-as-code runs, branch and pull-request workflows, or a feature dependency and release plan.

## Questions to ask first

Ask these in one round, and only about the facts the brief leaves open. Each question gives the default you would otherwise draw, so the user can reply "yes to all" or correct one item.

1. What are the stages, in order, from trigger to production? (default: commit, build and unit tests, publish artifact, deploy to staging, approval, deploy to production)
2. Which security or quality checks run, and at which stage? (default: only the checks the brief names; no SAST, SCA or DAST is added on our own)
3. Which gates block the pipeline and which only warn? (default: test failures and named policy checks block; everything else is reported without blocking)
4. Who approves what, and is the approval a person or an automated policy? (default: one human release approval before production only)
5. Which environments exist, and does the same artifact move through all of them? (default: staging and production, with one artifact built once and promoted by digest)
6. What is the deploy target, and is delivery push or pull? (default: a Kubernetes cluster, deployed by the CD stage pushing a Helm release; GitOps only if the brief says so)
7. How is the new version rolled out: rolling update, blue/green, or canary with automated analysis? (default: a Kubernetes rolling update; no traffic splitting drawn)
8. If the brief mentions rollback: what detects the failure, and what tool performs the rollback? (default: rollback is drawn only if the brief mentions it; then deploy verification, such as a Helm wait timeout or a post-deploy smoke test, fails and the CD tool rolls back to the previous release; no automatic database rollback)
9. Are artifacts signed, and is a signature or provenance checked before the workload runs, against which signer identity or key? (default: no signing is drawn unless the brief mentions signing, SBOM, provenance or admission)
10. If the brief covers credentials: how does CI reach the registry and the deploy target, and how do workloads get secrets? (default: credentials are not drawn; when they are, CI uses OIDC federation to short-lived, least-privilege credentials that can push to the registry and deploy only into its namespace, with no long-lived keys in CI, and workloads read production secrets from the vault at runtime, not from CI)
11. For infrastructure as code: who runs plan and apply, is the plan checked by policy, and is apply gated by approval? (default: plan on the pull request, policy check on the plan, human approval, then apply the same saved plan under state locking; re-plan and re-review if state changed; plan files kept as protected artifacts because they can contain secrets)
12. For branching or release plans: which long-lived branches exist, where do releases come from, and which features depend on which? (default: short-lived feature branches merged to main through a reviewed pull request, releases tagged from main, dependencies only as stated, no dates drawn)

## Push back when

- The brief rebuilds the artifact for each environment but also claims end-to-end provenance. Provenance and signatures describe one specific build output; rebuilding produces different artifacts, so the usual pattern is build once and promote the same digest.
- The brief deploys by a mutable tag (such as `latest`) and says the deployment is pinned or verified. A tag can be moved to different content; signature checks and pinning refer to the image digest.
- The brief treats an SBOM as a security scan or a gate. An SBOM is an inventory of components; it only blocks a release if a separate check evaluates it against a policy or vulnerability data. Ask whether that check exists.
- The brief says a signature proves the image is safe. A signature shows who produced the artifact and that it has not changed since; it says nothing about vulnerabilities.
- The brief verifies that an image is signed but does not say by whom. A check that only requires some signature proves little, especially with keyless signing, where anyone can obtain a valid short-lived certificate. Ask which identity or key the admission policy requires; with keyless signing the policy must pin the issuer and subject.
- The brief claims a SLSA level or unforgeable provenance, but the provenance is generated by a build step the user controls, or builds run on a persistent shared runner. SLSA Build L3 needs provenance generated by the build platform and isolated builds. Ask who generates and signs the provenance and whether builds are isolated.
- The brief runs pull-request builds with the same credentials or runners as release builds. Untrusted pull-request code can then read secrets or poison caches and artifacts. Ask whether PR jobs run without secrets on isolated, ephemeral runners.
- The brief places DAST before the build or on source code. DAST tests a running application, so it needs a deployed test or staging environment. SAST reads source code; SCA reads dependency manifests or the built artifact.
- The brief calls the design GitOps but the CI job pushes changes directly into the cluster. In GitOps, an agent in or near the cluster pulls desired state from a Git repository and reconciles it; CI changes the repository, not the cluster. Ask which model they run.
- The brief rolls back a GitOps deployment by changing the cluster by hand. If the reconciler has auto-sync and self-heal or drift correction on, it restores whatever Git declares, so the manual change is undone. Durable rollback is a revert in the configuration repository. Ask whether self-heal is enabled and whether out-of-band rollbacks (with auto-sync paused or reconciliation suspended) are allowed.
- The brief expects a failing health probe to redeploy the previous release by itself. A failing readiness or liveness probe stalls the rollout or restarts pods; a rollback only happens if a tool acts on it (a Helm rollback-on-failure option, progressive-delivery analysis, a smoke-test job or an alert-driven CD step). Ask which one.
- The brief expects rollback to undo database migrations or data changes. Redeploying the previous release does not reverse a schema migration; ask whether migrations are backward compatible or have their own down step.
- The brief applies infrastructure changes from a plan other than the one reviewed or policy-checked. The reviewed plan must be the one applied. A saved plan that has gone stale because state changed must be re-planned and re-reviewed, not forced through.
- The brief puts signature verification only in CI and calls it admission control. Admission control runs when the workload is submitted to the cluster; a CI check alone does not stop an unsigned image deployed by another route.

## How we draw it here

- Layout: stages run left to right in the order the user gave, one stage per column. Group environments or trust zones with `boundary` groups and phases such as "Build" or "Release" with `panel` groups. For people-and-team workflows (branching, PR review, change approval) use stacked `lane` groups, one lane per role or per branch, as in DESIGN_SYSTEM.md.
- Stages: `component` cards with a verb-object label and the tool or owner as `detail`. Use `devops/source-code` or `devops/git-repository` for the source, `devops/pull-request` and `devops/code-review` for review, `devops/ci-build` for build, `devops/unit-tests`, `devops/integration-tests`, `devops/end-to-end-tests` for tests, `devops/artifact-registry` and `devops/container-image` for the artifact, `devops/cd-release` for deploy, `devops/rollback` for rollback. Use `devops/sast`, `devops/sca`, `devops/dast`, `devops/sbom`, `devops/policy-as-code` only for checks the brief names.
- Gates: an automated gate is a `symbol` node using `presentation/decision` with a question `caption` ("Policy passed?") and labelled "Pass" and "Fail" branches. A human approval is `devops/release-approval` (or `business/approval` in a process lane). A failed branch ends at `status/blocked` or loops back as feedback. A warn-only check has no fail branch; label its outgoing edge "Report" and say "warn only" in its `detail`.
- Rollout strategy: for canary or blue/green, add a `presentation/decision` analysis gate and a traffic-shift step card ("Shift 10% traffic", "Switch to green") before promotion. A rolling update needs no extra step.
- Rollback, when the brief has it: the trigger is the condition the brief names, drawn as `observability/health-probe` or `observability/alert` feeding a `presentation/decision`, then a `feedback` edge to `devops/rollback`. Name the tool that performs the rollback in its `detail`.
- Supply chain: put `identity/key` or `identity/certificate` on the signing step ("Sign image", with the signer identity in `detail`), and `identity/certificate-authority` if a CA or keyless issuer is part of the story. When keyless signing is used, add an `observability/audit-log` card labelled "Transparency log". There is no provenance asset; draw provenance as an `identity/certificate` card labelled "Provenance attestation" next to the build that produces it.
- Admission: admission is not a proxy in front of the API server. Draw the deploy request going to `kubernetes/control-plane`, a `control` edge from the control plane to `security/policy-engine` labelled "Admission review" (detail: "webhook called by API server", plus the required signer identity or key), and the allow or deny decision coming back to the control plane.
- GitOps, Helm and operators: `devops/git-repository` labelled "Config repository", a reconciler as `kubernetes/operator` labelled with its role, `kubernetes/helm-chart` for charts, `kubernetes/namespace` and `kubernetes/deployment` for targets. Draw the edge from the repository to the reconciler, labelled "Pull desired state".
- IaC: `devops/infrastructure-as-code` for the code, a stage card for plan, `devops/policy-as-code` for the policy check, `devops/release-approval` for approval, then apply into the `cloud/vpc`, `cloud/cloud-region` or other `cloud` target the brief names.
- Identity and secrets, when the brief covers credentials or trust zones: draw CI and production as separate `boundary` groups. Use `identity/federation` when CI trades its job identity for cloud or registry credentials, `identity/access-token` for the short-lived credential, `identity/service-account` for a named CI or workload identity, and `identity/secrets-vault` inside the production boundary. Draw PR validation and release publishing as separate identities when both appear.
- Feature or release plans: `presentation/step` or component cards per feature, `dependency` edges from the dependent item to the item it needs, `business/calendar` only when a date is stated, and `status/pending`, `status/approved` or `status/blocked` as markers.
- Edge meanings: `data` (solid) for artifact or change flow (commit, image, chart, plan); `control` for triggers, approvals and policy decisions; `feedback` for failures, rework and rollback; `dependency` (dotted) for feature or stage dependencies. The renderer colours edges only by `palette`, and `control` and `feedback` share the same dash, so set `palette: "orange"` on control edges and `palette: "red"` on feedback edges, or they render identically. Add a `legend` whenever more than one meaning appears, with matching `palette` and `dashed` values.
- Palettes: keep one palette per zone (for example purple for CI, teal for production), orange for control, and red only for failure paths. Colour never replaces a label.
- Write `description` as the flow in one or two sentences, and keep the standard `footer` stating that labels describe roles and symbols do not assert product compatibility.

## Common mistakes

- Adding SAST, SCA, DAST, an SBOM step, a vault, federation or a health probe because typical pipelines have them. Draw only what the brief names or the user confirmed.
- Drawing every gate as a plain arrow labelled "Pass" with no fail branch, so blocking and warn-only checks look the same.
- Using `data` edges for triggers and approvals, or leaving `palette` unset on `control` and `feedback` edges so they look the same.
- Showing signing with no key or certificate, or a signed image with nothing that verifies it, or a verification with no required signer identity.
- Drawing the admission policy engine inline in front of the control plane instead of being called by it.
- Drawing a git commit graph with commit dots on branch rails. The kit has no commit-graph notation; use one lane per branch with step nodes and merge edges between lanes.
- Placing rollback as a normal forward stage after deploy, or implying that a health probe rolls back by itself, instead of a `feedback` path from a named trigger through a decision.
- Showing CI with a direct line to production secrets or the production cluster when the brief describes a pull-based or vault-mediated design.
- Picking `software/workflow` or `software/scheduler` as a stand-in for CI, or `cloud/public-cloud` for an unnamed deploy target. Use `devops/ci-build` and ask for the target.
- Drawing a gate as a `component` instead of a `presentation/decision` symbol with a caption.
- Implying that the pipeline approval also approves infrastructure changes when the IaC apply has its own gate, or the reverse.

## Start from

- `secure-ci-cd` for a pipeline with build, checks, approval, deploy and rollback. It needs these edits: replace the `devops/sca` "Security checks" card with the checks the brief names (or remove it); replace the "Pass" `data` edge with a `presentation/decision` gate that has Pass and Fail branches; change the "Approve" edge to `control` with palette orange; redraw "Restore" as a `feedback` edge (palette red) into `devops/rollback`, triggered by `observability/health-probe` or `observability/alert`, or remove rollback if the brief does not mention it.
- `eng-platform-delivery` for a swimlane of developer, reviewer, CI and platform roles, and for branch or pull-request review workflows. Treat its `devops/sast` "Security scan" card the same way, and change the "Go" `data` edge out of release approval to a `control` edge with palette orange.
- Supply-chain, GitOps, IaC and release-plan diagrams: no template yet; use `layout_diagram`, then adjust positions to left-to-right stages.
- Read alongside: `brief` and `style` always; `kubernetes` for cluster, Helm, admission and operator targets; `security-architecture` for identity, signing and secrets boundaries; `business-process` for swimlane conventions.
